# 1. 目的

本書は、Google Apps Scriptを実行環境として利用する本システムを、安全かつ再現可能な方法で開発・レビュー・デプロイ・検証するための運用ルールを定義する。

---

# 2. 基本方針

開発環境と実行環境を分離する。

```
Git
  = 開発SSOT

GAS
  = 実行環境・実機検証環境
```

GAS IDEを開発SSOTとして扱わない。

---

# 3. SSOT

唯一の開発SSOTはGitリポジトリとする。

対象：

```
https://github.com/somurye/home-ai-assistant
```

Gitに存在しないGAS側の変更は正式な開発成果物として扱わない。

なお、個々のタスクの詳細定義(目的・対象ファイル・変更許可/禁止ファイル・完了条件・テスト条件・証拠・レビュー強度)は `docs/TASK_PLAN.md` をSSOTとする。本書はタスク横断の運用ルールを定める。

---

# 4. 開発フロー

標準フロー：

```
1. タスク仕様確定(docs/TASK_PLAN.mdの該当タスク定義を確認)
2. Geminiへ実装指示
3. Gemini実装
4. タスク用Gitブランチ上でGit diff確認・テスト・commit
5. Qwen SOレビュー(Gitのブランチ差分・実ファイルを監査)
6. PMレビュー(Gitのブランチ差分・実ファイルを監査)
7. PM承認
8. merge
9. clasp push
10. GAS実機テスト
11. テスト結果をGitへ記録
12. Task Complete
```

TASK-002以降は、レビュー対象をタスク用Gitブランチとそのcommitで固定する。実装・テストを終えた時点のcommitが存在しない状態で、Qwen SOレビューまたはPMレビューを開始してはならない。

PM承認はmergeの承認であり、merge自体、GAS同期、実機テスト、およびTask Completeを自動的に完了させるものではない。

---

# 5. TASK-000

TASK-000は「開発基盤・運用基盤構築」とする。

TASK-000ではアプリケーション機能を実装しない。

対象：

* Gitプロジェクト
* ディレクトリ構成
* 基本ドキュメント
* clasp
* GASプロジェクト接続
* 開発ルール
* テストルール
* レビュー運用

**状態:完了。**

以下を満たすこと。

- [x] Gitリポジトリが存在する
- [x] 基本ディレクトリが存在する
- [x] 仕様書が存在する(`docs/SPEC.md`)
- [x] 開発運用仕様書が存在する(本書)

**TASK-000は上記すべてを満たし完了済み。** TASK-001以降は `docs/TASK_PLAN.md` の各タスク定義に従って進める。

---

# 7. clasp運用

claspをGAS同期の標準手段とする。

基本操作：

```
Git上で編集
 ↓
commit
 ↓
clasp push
 ↓
GAS
```

GAS IDEでコードを直接編集してGitへ戻す運用を基本ルートにしない。

---

# 8. GAS側の扱い

GASは以下の目的に限定する。

* 実行
* 実機テスト
* Googleサービスとの実環境連携確認
* デプロイ確認

GASを独立した開発ブランチとして扱わない。

---

# 9. GAS直接編集禁止

原則としてGAS IDEからコードを直接変更しない。

緊急対応等で直接変更した場合でも、正式な作業として扱うにはGit側へ変更を還流する。

---

# 10. GitとGASの同期確認

実機テスト開始前にGitとGASの同期状態を確認する。

不一致が確認された場合は、原因を特定し、SSOTをGit側へ戻してからテストを継続する。

---

# 11. タスク単位の変更管理

各タスクには以下を定義する。

* TASK-ID
* 目的
* 対象ファイル
* 変更許可ファイル
* 変更禁止ファイル
* 完了条件
* テスト条件
* 証拠

**TASK-001以降、これらの項目は個別に本書へ記載せず、`docs/TASK_PLAN.md` に一元化して記載する。** 本書は上記項目の定義ルールのみを保持する。

---

# 12. 変更許可ファイル

Claude等のAIへ実装を依頼する場合、変更対象ファイルを明示する。

対象外ファイルを勝手に変更してはならない。

対象ファイルの一覧は `docs/TASK_PLAN.md` の該当タスク定義を参照する。

---

# 13. 変更禁止ファイル

タスクごとに変更禁止ファイルを明示する。

レビュー時には以下を確認する。

```
git diff --name-only
```

仕様にない変更が存在する場合は、理由を確認する。

変更禁止ファイルの一覧は `docs/TASK_PLAN.md` の該当タスク定義を参照する。

---

# 14. スコープ管理

以下を禁止する。

* 未依頼のリファクタリング
* 将来機能の先行実装
* 無関係なファイル変更
* 仕様変更の独断実施
* テストの都合による仕様変更

必要な仕様変更は別途タスク化する。

---

# 15. Geminiの役割

Geminiは主実装者とする。

担当：

* コード実装
* テスト実装
* 修正
* 実装報告
* タスク用Gitブランチへのcommit

Gemini自身が「完了」と判断しても、PMレビュー完了とはみなさない。

Geminiの完了報告では、コンテキスト圧迫を避けるためコード全文を原則として貼らない。Gitを正本とし、少なくとも以下を報告する。

* TASK-ID
* 実装状態(Code Complete)
* ブランチ名
* commit ID
* 変更ファイル
* 変更禁止ファイルに変更がないこと
* 実装概要
* テスト結果
* 未実施の工程(Qwen SO、PMレビュー、merge、clasp push、GAS実機テスト等)
* 問題・懸念

コード本文、個別ファイルの全文、または追加の証拠が必要な場合は、Git上の対象ブランチ・commit・実ファイルを参照する。報告文へコードを重複掲載してレビュー対象を分散させない。

---

# 16. Qwenの役割

Qwenはコード・仕様・実装のSOレビュー担当とする。

QwenはGeminiの報告文をコードの正本として扱わず、指定されたタスク用Gitブランチのcommit、ブランチ差分、および必要な実ファイルを監査する。コード全文が必要な場合も、報告文への再掲ではなくGit上の実ファイルを取得して確認する。

確認事項：

* 仕様適合
* スコープ逸脱
* 実装上の問題
* テスト不足
* セキュリティ
* データ整合性
* GAS固有問題

---

# 17. Qwenレビューの強度

すべての変更を同じ深度でレビューする必要はない。

### Level A：厳格レビュー

以下は必須。

* Gemini API連携
* OCR
* Spreadsheetデータ更新
* 在庫ロジック
* データモデル変更
* 認証・権限
* 外部サービス連携
* 共通サービス変更
* エラー処理
* セキュリティ関連

### Level B：通常レビュー

* UIロジック
* 通常の業務ロジック
* GASサービス追加
* テスト変更

### Level C：軽量レビュー

* README修正
* コメント修正
* 文言修正
* 軽微なドキュメント修正

Level Cでは完全レビューを省略できる。

各タスク(TASK-001〜TASK-008)に適用されるレビュー強度は `docs/TASK_PLAN.md` に明記する。

---

# 18. PMレビュー

Qwenレビュー後、PMが最終判断を行う。

PMはQwenと同様に、対象タスク用Gitブランチのcommit、ブランチ差分、および必要な実ファイルを正本として確認する。Geminiの完了報告は工程状況の要約であり、コード監査の代替ではない。

PMは特に以下を確認する。

* 仕様どおりか
* 余計なことをしていないか
* 変更禁止ファイルが変更されていないか
* 証拠があるか
* テストが十分か
* 実機検証が必要か

---

# 19. 完了状態

タスク完了には複数の状態を区別する。

```
Code Complete
↓
Review Complete
↓
PM Approved
↓
Merge Complete
↓
GAS Sync Complete
↓
GAS Test Complete
↓
Task Complete
```

`Code Complete` は、タスク用ブランチに実装・テスト結果をcommit済みで、レビュー可能な状態をいう。`Review Complete` は、必要なレベルのQwen SOレビューが完了した状態をいう。`PM Approved` は、PMがmergeを承認した状態をいう。`Merge Complete` は、承認済みの変更が対象ブランチへmergeされた状態をいう。

`Merge Complete` は `Task Complete` ではない。merge後にclasp push、必要なGAS実機テスト、およびテスト結果のGit還流を完了して初めてTask Completeとする。単にコードがGitへ存在するだけではTask Completeとしない。

---

# 20. Rule 1：仕様先行

実装前に仕様を確定する。

AIに曖昧な要求を直接与えて実装させない。

---

# 21. Rule 2：SSOT優先

Gitを正本とする。

GAS IDE上のコードを正本として扱わない。

レビューでは、タスク用Gitブランチのcommit、差分、および実ファイルを正本として扱う。AIの実装報告に掲載されたコード断片またはコード全文を正本として扱わない。

---

# 22. Rule 3：変更範囲固定

タスクで許可されたファイル以外を変更しない。

---

# 23. Rule 4：AIによる仕様拡張禁止

AIが「より良い設計」と判断しても、未依頼の仕様追加を行わない。

必要な改善は別タスクとして提案する。

---

# 24. Rule 5：証拠優先

「動くはず」「実装した」は証拠として扱わない。

必要に応じて、

* Git diff
* テスト結果
* 実行ログ
* スクリーンショット
* GAS実機結果

を提示する。

---

# 25. Rule 6：テスト分離

コードテストと実機テストを分ける。

```
Git側
  ↓
コード・単体テスト

GAS
  ↓
実機・Googleサービス連携テスト
```

---

# 26. Rule 7：GAS実機検証

スマートフォンを含む実環境で動作確認が必要な機能は、GASへ同期した上で実機確認する。

特に以下：

* カメラ入力
* 画像アップロード
* Gemini OCR
* モバイルUI
* Spreadsheet書き込み
* Drive保存

---

# 27. Rule 8：実機結果のGit還流

GASで発見した問題をGAS側だけで修正して終わらせない。

```
GAS実機テスト
 ↓
問題発見
 ↓
Git側で修正
 ↓
レビュー
 ↓
commit
 ↓
clasp push
 ↓
再テスト
```

---

# 28. Rule 9：報告してから修正

問題を発見したAIは、まず以下を報告する。

* 問題
* 原因
* 影響範囲
* 修正案
* 変更予定ファイル

PMの承認なしに大規模な修正へ移行しない。

---

# 29. Spreadsheetアクセスルール

Spreadsheet APIは原則バッチ処理とする。

推奨：

```
getValues()
 ↓
メモリ処理
 ↓
setValues()
```

禁止：

```
ループ
 ↓
getValue()
 ↓
setValue()
 ↓
次のループ
```

---

# 30. 画像入力ルール

スマートフォンから取得した画像をそのままGASへ送信しない。

ブラウザ側で、

```
撮影
 ↓
リサイズ
 ↓
圧縮
 ↓
Base64
 ↓
GAS
```

とする。

画像サイズ・圧縮率は実装時に測定して決定する。

---

# 31. 商品名正規化ルール

商品名の正規化をGeminiの出力だけに依存しない。

将来的に、

```
Gemini候補
 ↓
GAS
 ↓
商品マスタ照合
 ↓
候補提示
 ↓
ユーザー確認
```

とする。

商品マスタの本体実装は専用タスクで行う。

---

# 32. Spreadsheetデータ保護

Geminiから得たデータを直接Spreadsheetへ書き込まない。

必ず、

```
Gemini
 ↓
Schema検証
 ↓
業務ルール検証
 ↓
必要ならユーザー確認
 ↓
Repository
 ↓
Spreadsheet
```

とする。

---

# 33. SheetRepositoryの責務

Spreadsheetへのアクセスは `SheetRepository.gs` に集約する。

業務サービスが直接多数のSpreadsheet APIを呼び出す構造を避ける。

---

# 34. APIキー管理

APIキーをGitへ保存しない。

GASのPropertiesService等を利用する。

---

# 35. 環境依存値

以下をソースコードへ直接埋め込まない。

* Gemini APIキー
* Spreadsheet ID
* Drive ID
* GAS固有設定
* 本番環境固有値

---

# 36. テスト報告

実機テストを実施した場合、結果をGit上のテストレポートへ記録する。

最低限：

* TASK-ID
* 実施日時
* 環境
* 端末
* 入力
* 期待結果
* 実結果
* PASS/FAIL
* 問題

---

# 37. テスト失敗時

テスト失敗をもって即座に実装変更を開始しない。

まず、

```
失敗内容
 ↓
再現条件
 ↓
原因仮説
 ↓
影響範囲
 ↓
修正方針
```

を整理する。

---

# 38. AIレビューの役割分担

* Gemini:実装
* Qwen:技術・仕様レビュー
* ChatGPT:PM視点レビュー・スコープ判断
* 人間:最終承認

各AIの判断を無条件に正しいものとして扱わない。

---

# 39. 仕様変更

仕様変更が必要になった場合は、コードを先に変更しない。

原則：

```
問題発見
 ↓
仕様変更案
 ↓
仕様書更新
 ↓
タスク更新
 ↓
実装
```

---

# 40. 緊急修正

GAS実機テスト中に重大障害が発生した場合も、可能な限りGit側を修正してからclaspで再同期する。

直接GAS修正が避けられない場合は、必ず変更内容を記録し、Gitへ還流する。

---

# 41. タスク完了判定

以下をすべて満たした場合にTask Completeとする。

* 実装完了
* テスト完了
* Qwenレビュー完了(対象レベルに応じる)
* PMレビュー完了
* Git commit済み
* PM承認後にmerge済み
* GAS同期済み
* 必要な実機テスト済み
* テスト結果記録済み
* GitとGASの状態一致

---

# 42. 開発原則

本プロジェクトの開発原則を以下に定める。

> **Gitで作り、AIでレビューし、人間が承認し、claspでGASへ同期し、実機で検証する。**

そしてシステム開発そのものについては、

> **AIの曖昧さを、GASの厳格なルールとUIの確認ステップで制御する。**

この2つを本プロジェクトの基本原則とする。
